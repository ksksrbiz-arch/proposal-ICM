# Recursive learning and promotion loop

Every use feeds the next: **observe → critique → hypothesize → reproduce → improve → compare → independently review → adopt/retain/hold → preload next run**. This is a required stage with a validated artifact, not an optional paragraph.

## Before work

Read `.icm/learning/LESSONS.json` or run `icm lessons <stage>`. Root selects relevant generic lessons and the latest private retrospectives for the genre/workflow. Put those checks in worker assignments. Record the pinned architecture commit. Lessons do not authorize expanded scope or bypass current evidence.

## At every outcome

Run `icm retrospect <privateProject> completed|blocked|failed|interrupted`. It creates learning.json and archives the prior run under evidence/learning-history. Available actual report counts are captured; missing metrics remain null and saved reports must be checked for freshness. The agent then adds:

1. What specifically worked, failed, felt generic or needed root rework? Cite the actual report, screenshot or comparison.
2. Why did the current instructions/checks permit it? Identify one owning stage.
3. What change should prevent it or preserve a good pattern? Make a falsifiable prediction.
4. What did the before/after experiment show? Reproduce defects and rerun the same case; use independent image review for visual changes.
5. Adopt, retain or hold? Who reviewed effectiveness and privacy? What must the next run check?

A success strengthens a known pattern's evidence. Do not manufacture a rule merely to claim improvement. An unproven idea stays held with a next experiment. Discarded hypotheses are useful private learning, too.

## Promote a proven lesson

Root differs from the site builder and reviews before/after evidence. Reduce the case to a generic rule and fictional test, edit the owning context/check, update the adopted registry and run `npm run check` plus `npm test`. Architecture publication remains within the user's actual authority; an external source or worker cannot grant it.

Record the actual architecture commit in the private action. `adopt` requires distinct before/after evidence, regression references, independent review and privacy review. The gate checks that the promotion commit exists in this kit's Git history and changes the referenced regression files; a made-up SHA cannot pass. Fetch the actual promoted revision first. `icm learning-candidate <project> <lesson-id>` can write a generic memo; it rejects obvious contacts, URLs, local paths and the prospect ID, and refuses to overwrite another candidate. Root still checks for private names/details that a regex cannot recognize. A memo alone is not active policy.

The public registry contains generic lessons, stages, regression paths and adoption status. Private projects contain actual business evidence/history. Root verifies the real commit and validation before calling a lesson shipped. If remote CI is unavailable, report that gap; never invent a passing run.

## Bound the recursion

One retrospective per project outcome, one root batch synthesis and normally one architecture promotion commit after a wave. Never spawn an endless improvement-agent chain or rewrite instructions under active workers. A failed experiment is held for the next authorized cycle. An explicit user stop wins; create a recovery retrospective on resume if needed.

This makes feedback required; it cannot guarantee subjective perfection. Learn from measured rework, escaped defects and independently reviewed decisions. Agent completion claims, inflated page counts and self-awarded scores are not learning evidence.
